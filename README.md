# SemStore

## О проекте

**SemStore** — это приложение для оформления заказов из Китая.
Проект вырос из реального бизнеса и был создан для замены ручной работы и общения в личных сообщениях на систему с понятным жизненным циклом заказа.

Приложение выступает посредником между пользователями и товарами, позволяя: создавать адреса доставки, оформлять заказы, добавлять товары, отслеживать статусы и централизованно управлять проверкой и обработкой заказов со стороны администратора.

Проект реализован в виде микросервисной архитектуры с безопасностью и асинхронным взаимодействием между сервисами.

---

## Основные возможности

### Пользователь 
- Регистрация и аутентификация (JWT access + refresh).
- Управление адресами доставки:
  - создание/обновление/удаление,
  - “мягкое удаление” адреса (флаг `deleted`) с последующим удалением после завершения связанных заказов.
- Управление заказами:
  - создание заказа на выбранный адрес,
  - добавление/обновление/удаление товаров в заказе,
  - подтверждение заказа для передачи на проверку администратору,
  - просмотр заказов с пагинацией и фильтрацией (по статусу и диапазону дат).
- Отслеживание статусов заказа по жизненному циклу.

### Администратор (роль `ROLE_ADMIN`)
- Просмотр всех заказов в системе с пагинацией и фильтрацией.
- Получение заказа по ID.
- Проверка заказа и управление этапом подготовки к оплате:
  - установка цен на товары (цены выставляет администратор),
  - перевод заказа в статус ожидания оплаты или возврат заказа пользователю для правок.
- Завершение заказа после доставки.
- Управление пользователями:
  - просмотр пользователей с ролями,
  - изменение роли пользователя.

## Архитектура проекта

- **API Gateway** — единая точка входа, валидация JWT, прокидывание `X-User-Id`, разграничение доступа к защищённым эндпоинтам.
- **Service Discovery** — регистрация и обнаружение сервисов.
- **User Service** — пользователи, роли, аутентификация/токены, адреса.
- **Order Service** — заказы, товары заказа, жизненный цикл заказа, административная проверка.
- **common-dtos** — общий модуль DTO/событий для межсервисного взаимодействия.

Асинхронная коммуникация используется там, где важно разделить ответственность сервисов и обеспечить слабую связанность.

## Сервисы

### `user-service`
- Регистрация/Авторизация пользователей, хранение учётных данных.
- JWT access/refresh (refresh token хранится в **HttpOnly cookie**).
- Роли `ROLE_USER` / `ROLE_ADMIN`.
- Управление адресами доставки.
- Поддержка сценария “мягкого удаления” адреса с последующим удалением после завершения заказов.

### `order-service`
- Создание и управление заказами пользователя.
- Управление товарами внутри заказа (ссылка, размер, цвет; цена выставляется администратором).
- Жизненный цикл заказа с бизнес-ограничениями по статусам.
- Админ-функции: проверка заказов, выставление цен, перевод в ожидание оплаты, завершение заказа.
- Outbox-логика для событий, связанных с завершением заказа и работой с адресами.

### `gateway`
- Валидация JWT.
- Прокидывание `X-User-Id` в order service.
- Контроль доступа к защищённым (в том числе admin) эндпоинтам.

### `discovery-server`
- Service discovery для микросервисов.

### `common-dtos`
- Общие DTO, используемые сервисами.

## Жизненный цикл заказа

Основной поток:

1. **PENDING** — заказ создан и отправлен на проверку в user-service (валидация пользователя/адреса).
2. **CREATED / CANCELED** — результат проверки:
   - `CREATED` — заказ валиден и доступен для добавления товаров,
   - `CANCELED` — заказ отменён из-за невалидных данных.
3. Пользователь добавляет товары и подтверждает заказ.
4. **IN_CHECK** — заказ передан на проверку администратору.
5. По результату проверки администратором:
   - **AWAITING_PAYMENT** — цены выставлены, заказ готов к оплате,
   - **CREATED** — возврат пользователю для правок (например, если товара нет в наличии).
6. **PAID** — заказ оплачен (статус оплаты фиксируется в системе).
7. **DELIVERING** — заказ в доставке.
8. **COMPLETED** — заказ завершён.

## Безопасность и аутентификация

- Аутентификация: **JWT access + refresh**.
- Refresh token хранится в **HttpOnly cookie**.
- Авторизация на основе ролей: `ROLE_USER`, `ROLE_ADMIN`.
- Gateway:
  - валидирует JWT,
  - добавляет заголовок `X-User-Id` для внутренних сервисов,
  - ограничивает доступ к защищённым эндпоинтам (admin API).

## Асинхронное взаимодействие и события

В проекте используется **Kafka** для асинхронного взаимодействия между сервисами.

### Оформление заказа
После оформления заказа (статус `PENDING`) указанный адрес проверяется в user-service на валидность и его доступность. Если адрес не существует/недоступен, статус заказа становится `CANCELED`, иначе `CREATED`. Вся эта логика реализовывается с помощью Kafka для асинхронного общения между order-service и user-service

### Outbox для событий
После завершения заказа в `order-service` создаётся outbox-событие (если с тем же адресом больше нет активных заказов).  
Далее событие отправляется в Kafka по расписанию.

Цель: корректно обработать сценарий удаления адреса:
- пользователь может “удалить” адрес (пометить `isDeleted`),
- связанные заказы должны доехать,
- после завершения заказов адрес удаляется окончательно.

## CI/CD

В проекте реализован CI/CD пайплайн.

### Pipeline включает следующие этапы:

1. **Сборка и тестирование**
   - сборка backend-модулей,
   - запуск unit и интеграционных тестов,
   - проверка корректности сборки перед деплоем.

2. **Сборка и публикация Docker-образов**
   - сборка Docker-образов для сервисов,
   - публикация образов в Docker Hub.

3. **Деплой на сервер**
   - обновление Docker-образов на сервере,
   - перезапуск сервисов через Docker Compose,
   - развёртывание обновлённой версии приложения без ручных действий.

CI/CD позволяет быстро и безопасно доставлять изменения в рабочее окружение,
минимизируя ручные операции и риск ошибок при деплое.

## Работа с базой данных

Проект использует PostgreSQL для хранения пользовательских данных и информации о заказах.  
Для ключевых сервисов используются отдельные БД: **users** и **orders**.

Для управления схемой применяется **Liquibase**: все изменения структуры БД выполняются через миграции.
